# 规格中心 (spec/)

本目录是本工程与 AI 智能体治理的**规格单一权威源（Single Source of Truth, SSOT）**。

工程严格遵循 **SDD（Spec-Driven Development，规格驱动开发）** 规范，所有业务功能均以功能独立目录形式沉淀，保证多规格独立推进、版本受控且互不干扰。

---

## 目录结构与功能定位

```
spec/
├── README.md                      # 本说明文件：规格目录定位与 SDD 资产全景
└── clue-lens/                     # 核心业务模块：线索洞察与全生命周期管理
    ├── raw-requirements.md        # 阶段 1：原始业务诉求（背景、痛点与粗粒度需求）
    ├── clarification.md           # 阶段 2：需求澄清结论（口径确认、边界划定与防雷决策）
    ├── requirements.md            # 阶段 3：正式需求规格说明书（SSOT 核心契约，含状态机、SLA 与 EARS 验收标准）
    ├── design.md                  # 阶段 4：技术架构与实现设计（表结构、Server Actions 与组件调用链路）
    └── tasks.md                   # 阶段 5：原子化任务分解清单（Checklist、依赖拓扑与验证命令）
```

---

## SDD 五阶段流转模型

在 AI 辅助全栈研发流水线中，各阶段通过标准化规范驱动流转：

1. **阶段 1：需求捕获 (`raw-requirements.md`)**：收集业务方痛点与功能诉求，保留原始背景。
2. **阶段 2：需求澄清 (`clarification.md`)**：针对异常流、数据归属、临界边界与性能指标发起反问，形成不可逆的业务决策。
3. **阶段 3：正式规格 (`requirements.md`)**：输出包含 EARS 验收标准、状态机流转规则与字段级契约的 SSOT 规格书。
4. **阶段 4：技术设计 (`design.md`)**：依据 `requirements.md` 与工程家规（`rules/`），输出符合 Next.js + Drizzle 架构的技术实现方案。
5. **阶段 5：任务分解 (`tasks.md`)**：拆解为具备可执行验证命令、单向依赖拓扑的原子化开发任务清单。

---

## 规格治理铁律

1. **统一根目录:** 所有业务规格、需求与契约均统一在 `spec/` 下管理，严禁在工程根目录下散落非标准的 `specs/` 或独立临时文档。
2. **规格先行:** 任何业务功能编码前，必须先查阅或订正对应功能目录下的 `requirements.md`，严禁“跳过规格直接改代码”。
3. **闭环验证:** 每个需求与规则变更，均需通过类型检查与确定性测试脚本（`check-consistency.mjs` 等）的回归验证。
