# 正式需求细化

<background_information>
- **成功标准**:
  - 所有验收标准遵循项目的 EARS 语法模式与约束
  - 同时覆盖业务需求和开发必须明确的技术需求
  - 核对澄清文档、原型、页面和现有系统的一致性
  - 不掺入数据库表结构、类设计、具体文件路径和实现代码
  - 当范围可能被误读时,显式写明包含/排除边界
  - 正式文档中不保留会影响用户行为、接口契约、权限、流程或验收结果的未决事项
</background_information>

<instructions>
## 执行步骤

1. **定位规格目录**:
   - 按以下顺序确定目标规格目录：
     1. 若用户明确提供 `spec/` 下的相对路径，将其作为目标路径。
     2. 若用户提供完整路径，确认其位于当前项目的 `spec/` 目录下，并转换为相对路径。
     3. 若用户未提供路径，但当前请求明确指向 `spec/` 下唯一的功能目录，可使用该目录，并向用户说明判断结果。
     4. 若存在多个候选目录或无法确定目标，不得猜测；在读取材料或写文件前先询问用户。
     5. `$1` 仅作为兼容写法，例如 `$1=platform/audit`，不假设调用环境一定提供位置参数。
   - 将最终确定的相对路径记为 `<spec-path>`；后续所有输入输出路径均使用 `spec/<spec-path>/...`。
   - 本阶段的唯一候选应包含 `clarification.md` 或其他已确认的澄清材料；如果用户只调用 `spec-requirements` 且无法确定唯一候选，先询问目标规格目录。

2. **加载上下文**:
   - 优先读取 `spec/<spec-path>/clarification.md`；若不存在，再读取该目录下其他已确认的需求澄清材料
   - 读取用户提供的原型、页面截图、Vue 页面、Markdown 说明、接口材料和相关业务附件（若用户明确给出）
   - 检查现有系统中同类页面、接口、权限、流程、字典和数据范围模式，识别可复用能力与兼容约束
   - 读取项目规则中与页面、接口、权限、流程和业务术语直接相关的部分

3. **阅读规则**:
   - 读取本 Skill 目录下的 `rules/ears-format.md` 了解 EARS 语法规则
   - 读取本 Skill 目录下的 `templates/requirements.md` 了解文档结构

#### 并行调研(Sub-Agent 分发)

以下调研方向彼此独立。请根据项目复杂度决定最优拆分——可拆分、合并、增加或跳过Sub-Agent。

**主上下文中处理**(正式需求必需):
- `spec/<spec-path>/clarification.md`、原型及其他已确认材料
- EARS 格式规则、需求模板

**委派给子代理**(把探索工作隔离在主上下文之外):
- **代码库线索**(存量项目):按需派一个Sub-Agent探索相关页面、接口、权限、流程和字典，让它总结已有能力、可复用模式和冲突。返回不超过 150 行的摘要。
- **领域调研**(需要外部知识时):派一个Sub-Agent做领域需求、标准或最佳实践的网络调研,返回精炼的结论摘要。

绿地新项目代码量极少时,跳过Sub-Agent分发,直接在主上下文加载。若多Sub-Agent能力不可用,则在主上下文中顺序执行。

全部调研完成后,先在主上下文中综合结论,再开始生成需求。

4. **执行一致性核对**:
   - 对照 `clarification.md`、原型/页面和现有系统，检查入口、字段、按钮、状态、流程、权限、数据范围及异常反馈是否一致
   - 将冲突分为需求口径冲突、原型缺口、现有系统约束和可复用能力
   - 会改变范围、权限、状态或验收结果的冲突必须先请用户确认；不得自行选择

5. **执行需求完整性确认门**:
   - 写正式需求前，逐项检查以下用户可见口径是否已经明确：
     - 页面入口、展示字段、查询条件、默认排序、分页行为和操作按钮
     - 表单必填、格式、范围、联动、重复提交和状态反馈
     - 多条数据或多字段变化的展示、分组和汇总方式
     - 功能权限、按钮权限、数据可见范围、敏感信息和越权结果
     - 业务状态、允许动作、流转条件及撤回、驳回、取消等异常路径
     - 空数据、失败、冲突、重试和无权限行为
     - 导入、导出、打印、附件等是否属于本期范围
   - 将未决事项分为：
     - **阻塞项**：会改变用户行为、页面结果、接口业务契约、权限、流程或验收结果。
     - **设计阶段项**：只决定数据库、类、组件、文件、算法或基础设施如何实现，不改变用户可见结果。
   - 存在阻塞项时，逐轮请用户确认，不得写入或更新正式 `requirements.md`，也不得用“后续设计确认”“开发时确定”代替需求结论。
   - 阻塞项只有在以下任一条件满足时才能关闭：用户明确选择口径；用户明确接受建议默认值；用户明确将对应功能移出本期范围。
   - 用户暂不确认时，只输出阻塞问题摘要并停止；不得生成带猜测或用户可见待定项的正式需求文档。

6. **生成正式需求草稿**:
   - 将需求组织为业务需求、页面需求、接口需求、权限需求、流程需求和非功能需求；无对应内容的分组直接省略
   - 页面需求写清入口、展示字段、查询条件、操作、表单校验和状态反馈
   - 接口需求写清业务用途、关键输入输出、错误语义和调用约束，不设计 URL、DTO 类或序列化实现
   - 权限需求写清功能权限、按钮权限、数据范围和越权结果
   - 流程需求写清状态、动作、角色、前置条件、流转结果和撤回/驳回等异常路径
   - 所有可验收行为使用 EARS 格式
   - 保持术语在各阶段的连续性:
     - 需求发现 = `Boundary Candidates`(边界候选)
     - 需求 = 必要时显式写明包含/排除与相邻预期
     - 设计 = `Boundary Commitments`(边界承诺)
     - 任务 = `_Boundary:_`
   - 若范围可能被误读,补充轻量的边界说明
   - 只允许把数据库表、字段类型、API URL、类和组件拆分、索引、缓存、算法等内部实现事项留到设计阶段
   - 正文不得出现“页面设计时确认”“技术需求阶段补充”“开发时确定”等推迟用户可见口径的表述
   - 先在对话中展示需求分组、范围边界和关键验收标准，请用户确认需求范围
   - 只有用户明确表示“确认需求”“按此生成”或同等含义后，才将需求草稿写入 `spec/<spec-path>/requirements.md`

## 重要约束

### 允许技术需求，禁止实现细节
正式需求既描述业务行为，也描述开发和联调必须明确的页面、接口、权限与流程契约；技术需求不等于技术实现。

**正式需求应包含:**
- 功能范围——包含什么、排除什么
- 用户可观察的行为——"X 发生时,用户应该看到/经历什么?"
- 业务规则与边界情况——限制、错误条件、特殊场景
- 页面入口、字段、按钮、交互、校验和反馈
- 接口的业务用途、关键输入输出和错误语义
- 功能权限、按钮权限、数据权限和越权行为
- 业务状态、角色动作、流转条件和异常路径
- 用户可感知的非功能需求——响应时间预期、可用性、安全级别
- 与现有系统的复用、兼容和相邻职责

**留到设计阶段:**
- 技术栈选择(数据库、框架、语言)
- 架构模式(微服务、单体、事件驱动)
- 数据库表、字段类型、索引和 DDL
- API URL、DTO/VO/Entity/Mapper/Service 类设计和具体文件路径
- Vue 组件拆分、内部组件结构和代码组织
- 非功能需求的实现方式(缓存策略、扩容方案)
- 属于设计的内部归属划分、组件接缝或实现边界
- 具体算法、伪代码和实现代码

**试金石**:如果内容决定用户、页面、调用方或验收人员能观察到什么，属于需求；如果内容决定代码、数据库或框架内部如何实现，属于设计。

### 其他约束
- 每条需求必须可测试、无歧义。若需求澄清材料在范围、行为或边界条件上存在多种解读,先请用户澄清再生成该需求。问题问够为止;不要生成含有自行假设的需求。
- “未提供原型”不等于可以推迟页面行为；仍须确认入口、字段、操作、校验、权限和反馈等可验收口径，具体布局和视觉样式可留到设计阶段。
- 为 EARS 语句选择合适的主语(软件类使用系统/服务名)
- requirements.md 中的需求标题必须以数字 ID 开头(例如:"需求 1"、"1."、"2 某功能……");不要使用字母 ID(如"需求 A")。
</instructions>

## 输出说明

1. **需求生成摘要**:主要需求分组的简要概览(3~5 条)
2. **完整性门禁**:说明是否存在阻塞项；存在时列出问题并明确未写入 `requirements.md`
3. **文档**:仅在用户确认需求范围且阻塞项清零后确认 `requirements.md` 已更新
4. **下一步**:阻塞项清零并确认正式需求后，才可进入 `spec-design`

**格式要求**:
- 使用 Markdown 标题保持清晰
- 文件路径放入代码块
- 摘要保持精炼(300 字以内)

## 安全与兜底

### 异常场景
- **缺少需求澄清材料**:若未找到需求澄清文档或已确认的需求澄清内容,向用户询问并补充特性范围、用户行为与边界条件
- **模板缺失**:若模板文件不存在,使用内置的兜底结构并给出警告
- **需求不完整**:在写盘前列出阻塞项并逐轮确认；用户未确认时停止，不生成正式 `requirements.md`
- **需求标题非数字 ID**:若既有标题没有数字 ID(例如"需求 A"),将其规范化为数字 ID 并保持映射一致(严禁数字与字母混用)
- **评审中发现范围歧义**:停止执行,不写入猜测的 `requirements.md`,请用户澄清缺失或冲突的范围后重新运行 `$spec-requirements <spec-path>`
- **用户要求推迟可见口径**:将对应功能明确移出本期范围，或继续保留为阻塞项；不得一边保留本期功能，一边把其验收口径推迟到设计或开发阶段
