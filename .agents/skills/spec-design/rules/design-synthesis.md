# 设计综合

完成本系统探索后、撰写设计文档之前，用以下三个视角审视核对结论。

## 1. 复用

先确认本系统是否已有可直接复用或小幅扩展的页面、接口、DTO、Service、Mapper、权限、流程和公共能力。

- 现有能力能满足需求时，沿用其文件落位、调用方式和业务口径。
- 小幅扩展即可满足时，优先扩展现有业务职责，不复制一套相似实现。
- 复用会改变现有行为或影响其他模块时，明确影响并谨慎选择业务私有实现。

## 2. 必要差异

只有 requirements.md 或现有能力确实要求时，才偏离本系统已有模式。

- 写明现有模式不能满足的具体需求或约束。
- 新增依赖、公共能力或技术模式前，先确认项目现有能力无法承接。
- 需求明确涉及外部契约且本地资料不足时，只核实对应官方资料；不得借此开展开放式架构选型。
- 将必要差异及理由直接写入 `design.md`；外部资料来源才写入 `research.md`。

## 3. 简化

对渐成形设计中的每个组件与抽象层,问一句:这真的有必要吗?

- 移除"以防万一"或为当前规格之外的假想需求而存在的组件
- 压平不必要的抽象层——若一个接口只有一个实现且看不到第二个,可能不需要这层间接
- 少而内聚的组件优于多而细碎的组件
- 正确的设计，是符合项目现有模式、满足全部需求且改动最小的设计
