# OA 业务系统技术设计原则

## 目标

技术设计应让开发人员无需猜测即可开始实现。重点说明具体文件、数据结构、核心业务逻辑和复杂流程，不为普通 OA、采购、审批或台账功能堆砌通用架构术语。

## 设计分级

- **轻量设计**：普通 CRUD、表单、列表和详情。覆盖页面与接口、文件清单、状态/权限、数据库变更、校验、异常和测试重点；不做外部调研、架构评选或形式化伪代码。
- **标准设计**：流程、权限、跨表事务、导入导出或较多业务规则。补充状态流转、事务边界、核心服务伪代码和关键异常。
- **深度设计**：外部系统、复杂计算、高并发、异步一致性或重大迁移。先深入分析本系统相关能力；仅在明确外部契约且本地资料不足时核实官方资料。
- 始终采用满足需求的最低级别，功能全新不等于技术复杂。

## 核心产出

### 1. 源代码文件清单

- 必须列出全部新增和修改文件，路径具体到文件名。
- 按前端、后端、配置/脚本/测试分组。
- 每个文件说明唯一的主要职责和关联需求 ID。
- 文件计划必须遵循当前任务相关的项目开发规范。
- 优先复用现有页面、DTO、Service、Mapper、权限和流程模式。
- 不因单个普通功能新增通用组件、通用服务或基础设施。
- 不允许只写“新增页面”“增加 Service”等无法执行的描述。

### 2. 数据库 DDL

仅在功能涉及后端持久化结构变更时编写：

- 提供适配目标数据库的可执行 DDL，不使用泛化伪 SQL。
- 包含表、字段、主键、必要索引、约束和注释。
- 说明字段业务含义、数据生命周期、历史数据处理和事务边界。
- 索引必须对应真实查询、排序、关联或唯一性要求。
- 纯前端功能或完全复用现有表时省略本章，并在方案概述中说明复用对象。

### 3. 核心服务伪代码

仅为包含业务判断、状态流转、权限校验、事务编排、聚合计算或跨表写入的服务编写：

- 写明入口、输入、输出、前置条件和业务异常。
- 伪代码表达执行顺序、关键分支、事务边界和持久化结果。
- 使用项目中的真实服务、领域对象和业务术语。
- 普通单表 CRUD 不写形式化伪代码，只说明校验、保存和返回规则。
- 伪代码不展开框架样板代码，也不替代最终实现。
- Java 项目必须使用 `java` 代码块和 Java 风格语法，引用真实存在或设计中明确新增的类、方法、DTO、Entity、Mapper、Service、异常和注解。
- 影响事务、AOP、审计、权限或异步行为的注解必须展示，例如 `@Transactional` 和项目实际使用的审计/权限注解。
- Java 项目禁止使用 `function`、`raise`、`begin transaction` 等语言无关写法。

### 4. 复用能力接入契约

只要复用平台或公共能力，就必须形成可独立指导开发的接入说明：

- 写明适用场景和不适用场景。
- 写明真实接入入口，包括注解、类、方法或服务接口。
- 写明关键参数、返回结果、上下文和前置条件。
- 存在多种接入方式时写明选择规则，例如注解式与编程式分别何时使用。
- 写明事务、AOP 代理、线程、权限和调用顺序等边界。
- 写明失败行为、降级方式和已知限制。
- 至少提供一个符合项目语言、使用真实名称的最小接入示例。
- 不得只写“复用现有能力”“按需接入”或仅列出类名。

### 5. 复杂流程时序

仅在后端复杂业务、跨服务调用、异步处理、流程审批或外部系统集成时编写：

- 优先使用 Mermaid `sequenceDiagram` 表达角色、页面、接口、服务、数据库和外部系统之间的调用顺序。
- 补充关键分支、失败、重试、补偿和最终一致性状态。
- 简单 CRUD 或单次查询不画图。
- 时序图与正文不得重复；正文只补充图中无法表达的业务规则。

## 简化章节

### 方案概述

- 用简短业务语言说明目标、范围、排除项、复用能力和关键约束。
- 普通业务功能不需要架构模式评选、分层理论或技术栈复述。
- 只有新增依赖、偏离现有技术栈或跨系统时，才说明技术选择及理由。

### 接口与页面协作

- 只列实现所需接口及关键入参、返回和权限。
- 普通字段不在接口、DTO、DDL 三处重复描述。
- 页面设计聚焦入口、查询展示、表单详情、操作权限和状态反馈。
- 前端页面必须遵守项目 `rules/` 中与表格、树、表单、上传、布局等相关的规范。

### 验证与风险

- 验证项只覆盖核心正常流程、权限/数据边界和关键异常。
- 风险只记录会影响开发、数据安全、兼容性或上线的真实问题。
- 不重复组织级通用测试、安全、性能规范。

## 需求追溯

- 使用 `requirements.md` 中的数字需求 ID，例如 `1.1`、`2.3`。
- 文件清单和验证重点应标注关联需求 ID，通常无需单独生成庞大的追溯矩阵。
- 每个需求至少应能对应到一个实现文件或明确的复用能力。
- 若需求无法映射到具体实现，先澄清需求或设计，不得用空泛描述掩盖缺口。

## 编写要求

- 使用声明式、具体、简洁的中文。
- 以现有代码库中的真实路径、类名、接口和模式为依据。
- 仅将不影响用户可见口径的设计实现信息标记为待确认，不得伪造现有文件、数据库对象或平台能力；需求层未决事项必须退回正式需求阶段。
- 同一内容只出现一次，其他章节通过引用关联。
- 与当前功能无关的模板章节直接删除，不保留“无”“不适用”之外的大段占位内容。
- 设计深度与业务复杂度匹配：简单 CRUD 保持短小，复杂业务才增加伪代码、时序图和异常分支。
- 不为寻找最佳实践、比较架构或升级技术栈进行开放式外部调研。
- 开始设计前确认 requirements.md 不存在影响用户行为、接口业务契约、权限、流程或验收结果的未决事项；存在时回到正式需求阶段。

## 人工评审清单

- 文件清单是否完整且路径可落地。
- 涉及数据变更时，DDL 是否可执行并符合业务口径。
- 核心服务伪代码是否覆盖关键规则、权限和事务。
- 复杂流程时序是否说明正常路径与主要失败路径。
- 是否遗漏接口、页面协作、历史数据或权限边界。
- 是否存在与需求无关的过度设计。
- Java 伪代码是否使用真实类、方法和注解，而非语言无关占位写法。
- 复用平台能力时，接入契约和不同接入方式的选择规则是否完整。
