# 并行任务分析规则

## 目的
在生成 `tasks.md` 时,提供一套一致的方法识别可安全并行执行的实现任务。

## 与任务排序的关系

`(P)` 的含义:本任务与紧邻的同级任务之间没有依赖,可与它们并发执行。任务排序原则(见 tasks-generation.md)保证基础阶段任务先行,因此核心阶段任务是主要的 `(P)` 候选。

## 何时可判定任务并行
仅当以下条件**全部**成立时,才将任务标记为可并行:

1. **无数据依赖**:不依赖任何未完成任务的产出。
2. **无文件冲突或共享可变资源**:不触碰相互冲突的文件或共享可变状态。
3. **无前置评审/审批**:不需要等待其他任务的评审或批准。
4. **基础工作已就绪**:本任务所需的环境/初始化工作已由更早的基础阶段任务完成。
5. **边界不重叠**:`_Boundary:_` 标注确认各任务作用于彼此独立的组件。

## 标记约定
- 在符合条件的任务的数字编号之后紧跟追加 `(P)`。
  - 示例:`- [ ] 2.1 (P) 构建邮件后台工作进程`
- 主任务与子任务都可以在符合条件时标 `(P)`。
- 若要求顺序执行(如带 `--sequential` 参数),完全省略 `(P)` 标记。
- `(P)` 保持在复选框方括号**之外**,避免与完成状态混淆。

## 分组与排序指南
- 属于同一主题的并行任务尽量归入同一父任务之下。
- 在细节要点中列出明显的前置条件或注意事项(如"依赖 1.2 的 schema 迁移")。
- 两个任务看起来相似但并非并行安全时,显式指出阻塞依赖。
- 仅作容器的主任务(自身没有可执行细节要点)不标 `(P)`——并行性在子任务层面评估。

## 质量检查清单
给任务标 `(P)` 之前,确认已经:

- 核实并发执行该任务不会造成合并或部署冲突。
- 确认 `_Boundary:_` 标注显示组件范围不重叠。
- 在细节要点中记录了共享状态方面的预期(如有)。
- 确认该实现可以独立测试。
- 若该 `(P)` 任务仍依赖其他主任务组的特定前置工作,已补充 `_Depends: X.X_`。

任一检查不通过,**不要**标 `(P)`,并在任务细节中说明依赖。
