# 任务生成规则

## 1. 任务描述

任务描述聚焦要实现的能力和可观察结果，同时引用 `design.md` 中已确定的文件职责，不重新发明技术设计。

应描述：

- 要实现的业务行为和规则。
- 需要新增或修改的职责范围。
- 数据、状态和流程如何变化。
- 完成后可观察或可验证的结果。

避免：

- 只有“处理逻辑”“完成接口”“实现页面”等模糊措辞。
- 在任务中新增 design.md 没有确定的类、表、接口或架构。
- 把多个可独立验证的结果塞进一个任务。

## 2. 任务来源

任务必须覆盖以下适用内容：

- `requirements.md` 中的全部数字需求 ID。
- `design.md` 源代码文件清单中的新增和修改文件。
- 数据库 DDL、迁移、初始化与历史数据处理。
- 核心服务伪代码中的校验、权限、事务、状态变化和持久化。
- 复杂流程时序中的职责节点、集成点和主要异常路径。
- 接口与页面协作、关键验证和真实风险。

每个需求至少对应一个任务；每个设计文件至少由一个任务承接，复用且无需修改的文件除外。

## 3. 排序与依赖

按实际依赖排序：

1. 基础准备：必要配置、公共类型、DDL/迁移和共享前置能力。
2. 核心实现：可独立开发的页面、接口、服务和数据访问。
3. 集成串联：前后端联调、跨职责调用和复杂流程闭环。
4. 验证收尾：关键正常流程、权限边界、异常与回归验证。

不需要的阶段直接省略。

任务顺序表示推荐执行顺序，但不自动构成对所有前序任务的依赖。只有确实需要前序产物时才构成阻塞依赖；不明显的依赖使用：

```markdown
_Depends: 1.2, 2.3_
```

直接依赖紧邻前项且从描述中显而易见时，可以不重复标注。

## 4. 职责边界

- 一个普通实现任务应落在单一职责或一组紧密相关的文件内。
- `_Boundary:_` 使用 `design.md` 文件清单中的职责组或具体文件范围，例如：
  - `_Boundary: 前端报表页面与页面私有组件_`
  - `_Boundary: 后端报表查询服务_`
  - `_Boundary: 报表定义表 DDL 与数据访问_`
- 跨前端、后端、数据库或外部系统的工作应设为显式集成任务。
- 标记 `(P)` 的任务必须声明 `_Boundary:_`，且边界不得与同组并行任务重叠。

## 5. 粒度与层级

- 任务粒度继承 `design.md` 的复杂度级别。
- 轻量任务通常为 0.5 至 1 人日，围绕一个完整业务能力组织，可合并紧密相关的页面、接口、Service、Mapper 和验证，不按每个文件机械拆分。
- 标准或深度任务通常为 1 至 3 小时；跨流程、权限、事务和外部集成按可独立验证结果拆分。
- 一个任务只包含一个主要可验证结果。
- 任务层级最多两级：主任务 `1.` 与子任务 `1.1`。
- 只有一个子任务时，折叠为主任务。
- 主任务仅作为分组容器时保持简短，细节放在子任务中。
- 不强制固定任务数量，根据实际文件和业务复杂度拆分。
- 普通 CRUD 不强制子任务、并行标记、`_Boundary:_` 或 `_Depends:_`；只有确有协调价值时才使用。

## 6. 可观察完成条件

每个可执行任务至少包含一条完成条件，明确完成后什么成立，例如：

- 页面可以按指定条件查询并展示正确结果。
- 接口在无权限时返回明确拒绝结果且不写入数据。
- DDL 可在目标数据库执行并创建所需约束和索引。
- 核心服务在事务中完成主数据、关联数据和操作日志写入。
- 集成流程从页面操作到数据持久化形成完整闭环。
- 对应测试或项目验证命令通过。

不要单独增加额外状态字段，完成条件直接写在任务细节中。

## 7. GWT 场景化验收规范 (Given-When-Then)

为了弥补 EARS 原子化规则缺乏“端到端用户业务旅程”连贯性的不足，任务生成器必须按以下规则生成 GWT 场景：

### 1) 触发与生成时机
- **必须生成 GWT 的场景**：当任务清单属于**标准/深度级别**，且涉及以下任意一种特征时，必须在**“集成串联与验证收尾”任务**（或核心业务闭环任务）中自动生成 GWT 场景用例：
  - 存在跨状态生命周期跃迁与审批/驳回闭环（如：待分派 -> 办理中 -> 待复核 -> 驳回退回）；
  - 存在多角色协同与视角切换（如：综合管理派发 -> 核查人员办理 -> 部门负责人终审）；
  - 存在大额资金、敏感权限防卫或外部复杂数据 Upsert 事务。
- **免除生成 GWT 的场景**：普通单表 CRUD、基础字典列表、静态页面布局和简单字段展示等轻量任务，**不强制生成 GWT**，仅保留单句“可观察完成条件”，避免任务清单形式化膨胀。

### 2) 数量与场景覆盖要求
对于包含 GWT 的任务，通常自动生成 **2 至 4 个**高价值具象场景：
- **正向黄金旅程 (Golden Path)**：至少包含 1 个完整的跨步骤业务端到端成功流转闭环。
- **逆向与异常阻断 (Unwanted Behavior / Edge Cases)**：至少包含 1 个驳回回退、状态机守卫拦截、越权拒绝或非法参数校验的防卫闭环。

### 3) 格式标准
GWT 场景必须直接写在对应任务的细节要点中，格式统一如下：

```markdown
  - **GWT 场景 1【正向黄金流转闭环】**:
    - **Given**: 系统处于某明确前置状态（如存在某编号线索，操作者为某角色）
    - **When**: 触发具体的用户动作或提交合法数据
    - **Then**: 产生预期的系统可观察状态跃迁或持久化结果
      **And**: 产生关联的历史留痕、通知或下游数据变化
```

## 8. 需求映射

每个任务细节末尾使用：

```markdown
_Requirements: 1.1, 2.3_
```

- 只写 requirements.md 中存在的数字 ID。
- 多个 ID 使用逗号分隔。
- 不追加描述、翻译、括号或自由文本标签。
- 任一需求缺少数字 ID 时停止生成任务，先修正 requirements.md。

## 9. 并行任务

默认允许分析并行性；使用 `--sequential` 时不添加 `(P)`。

轻量任务清单默认不做并行标记分析，除非用户明确要求或存在多个互不重叠的独立业务能力。

只有以下条件全部满足时才标记 `(P)`：

- 不依赖其他待完成任务的产物。
- 不修改相同文件或共享可变资源。
- 不需要等待其他任务的人工确认。
- 所需基础工作已经完成。
- `_Boundary:_` 显示职责和文件范围不重叠。

格式：

```markdown
- [ ] 2.1 (P) 实现报表查询页面
  - 页面可以按确认的条件完成查询并展示结果
  - _Requirements: 1.1, 1.2_
  - _Boundary: 前端报表页面与页面私有组件_
```

## 10. 可选测试任务

- 纯补充性、可推迟到 MVP 之后的测试覆盖可使用 `- [ ]*`。
- 可选测试必须直接引用已由核心实现满足的验收标准。
- 实现任务、关键集成验证、权限验证和数据一致性验证不得标为可选。

## 11. 增量更新

已有 `tasks.md` 时：

- 保留 `[x]` 完成状态。
- 保留 `_Blocked:_` 和 `## Implementation Notes`。
- 保留用户人工调整的任务描述、顺序和边界，除非新需求明确使其失效。
- 新增需求只追加或调整受影响任务，不无理由重排全部任务。
- 需求或设计变更影响已完成任务时，先报告影响并请求用户确认。

## 12. 写盘前自检

生成者在写入 `tasks.md` 前执行一次机械自检：

- 需求 ID 是否全部覆盖。
- 设计文件、DDL、核心服务和复杂流程是否都有任务承接。
- 涉及复杂状态流转与集成的标准/深度任务，是否生成了对应的 GWT 黄金验收场景。
- 编号、层级、依赖和并行标记是否自洽。
- 每个任务是否有交付物和可观察完成条件。
- 是否存在模板占位符、重复任务或孤立任务。

该自检不是审核或审批，不输出评审结论，不派发评审子代理，也不执行自动修复循环。发现任务本身的问题直接修正；发现 requirements.md 或 design.md 的真实缺口时停止并报告用户。

## 13. 任务范围

仅包含：

- 编码实现。
- 数据库 DDL、迁移与初始化。
- 技术配置和必要基础设施。
- 单元、集成、端到端和回归验证。

不包含：

- 生产部署和发布审批。
- 用户培训和用户验收组织。
- 营销、商务或项目管理活动。
- 与代码实现无关的说明文档任务。

## 14. 设计边界

- 优先承接 `design.md` 已确认的页面、DTO、Service、Mapper、权限和流程复用方案。
- 不因单个普通业务功能新增通用基础设施或抽象层。
- 不擅自改变 `requirements.md` 中的状态、权限、流程和验收口径。
- 发现需求、设计与任务无法一致时停止生成并回退到对应阶段，不在任务清单中自行补设计。
