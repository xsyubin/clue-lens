# 实现任务生成器

将已确认的需求和技术设计拆分为可执行、可验证、依赖清晰的实现任务，并写入 `spec/<spec-path>/tasks.md`。

## 执行流程

### 第 1 步：定位规格目录

- 按以下顺序确定目标规格目录：
  1. 若用户明确提供 `spec/` 下的相对路径，将其作为目标路径。
  2. 若用户提供完整路径，确认其位于当前项目的 `spec/` 目录下，并转换为相对路径。
  3. 若用户未提供路径，但当前请求明确指向 `spec/` 下唯一的功能目录，可使用该目录，并向用户说明判断结果。
  4. 若存在多个候选目录或无法确定目标，不得猜测；在读取材料或写文件前先询问用户。
  5. `$1` 仅作为兼容写法，例如 `$1=platform/audit`，不假设调用环境一定提供位置参数。
- 将最终确定的相对路径记为 `<spec-path>`；后续所有输入输出路径均使用 `spec/<spec-path>/...`。
- 本阶段的唯一候选必须同时包含已确认的 `requirements.md` 和 `design.md`；如果用户只调用 `spec-tasks` 且无法确定唯一候选，先询问目标规格目录。

### 第 2 步：加载上下文

读取：

- `spec/<spec-path>/requirements.md`
- `spec/<spec-path>/design.md`
- `spec/<spec-path>/tasks.md`（如存在，进入增量更新模式）
- 与本次实现直接相关的项目规范
- 本 Skill 的 `rules/tasks-generation.md`
- 非顺序模式下读取 `rules/tasks-parallel-analysis.md`
- 本 Skill 的 `templates/tasks.md`

约束：

- 显式调用本 Skill 表示用户要求基于当前 `requirements.md` 和 `design.md` 生成待人工评审的任务清单，不代表任务已经批准实施。
- 任一必需文件缺失时停止，并指出缺失文件及前置阶段。
- requirements.md 使用非数字需求 ID 时停止，先修正需求文档。

### 第 3 步：建立任务映射

先在工作记忆中建立映射，不立即写盘：

- 每个需求 ID 对应哪些用户可见行为和验证结果。
- `design.md` 中每个新增或修改源代码文件由哪个任务负责。
- 数据库 DDL、迁移或初始化由哪个后端任务负责。
- 核心服务伪代码中的校验、权限、事务和持久化由哪个任务负责。
- 复杂流程时序中的各职责边界、集成节点和异常路径由哪些任务负责。
- 接口与页面协作、关键验证和真实风险由哪些任务承接。

若需求或设计存在矛盾、关键文件职责不明、后端上下文缺失或无法拆成可执行任务，停止生成并向用户指出具体缺口，不自行补造设计。

### 第 4 步：生成任务清单

遵循 `rules/tasks-generation.md`：

- 先沿用 `design.md` 的轻量、标准或深度级别决定任务表达；不得把轻量设计扩张成重型任务计划。
- **轻量任务清单**：普通 CRUD、表单、列表和详情按完整业务能力拆分，可将紧密相关的页面、接口、Service、Mapper 和验证合为一个任务；通常 0.5 至 1 人日，不强制子任务、并行分析、`_Boundary:_` 或 `_Depends:_`。
- **标准/深度任务清单**：流程、权限、跨表事务、外部系统或复杂计算按基础准备、核心实现、集成串联、验证收尾排序；任务通常控制在 1 至 3 小时，必要时使用子任务、边界和依赖。在验证收尾或核心流程任务中，**自动生成 2 至 4 个具象化的 GWT (Given-When-Then) 端到端黄金验收场景**（覆盖正向主链路与关键逆向驳回/异常拦截）。
- 每个任务至少包含一个可观察的完成条件。
- 每个任务使用 `_Requirements:_` 映射数字需求 ID。
- `(P)` 任务必须使用 `_Boundary:_` 标注独立职责或文件范围。
- 不明显的跨组依赖使用 `_Depends:_` 标注。
- 轻量任务中前后端属于同一完整 CRUD 能力时可合并；只有存在独立交付、跨团队或复杂调用时才单设联调任务。
- 只生成编码、配置、DDL/迁移和验证任务，不生成部署、营销、用户培训等非开发任务。

### 第 5 步：生成者自检

本步骤是写盘前的机械自检，不是审核、评审、审批或通过裁决；不得派发评审子代理，不输出 `PASS`、`APPROVED` 等结论。

检查并直接修正草稿：

- 每个需求 ID 至少被一个任务覆盖。
- `design.md` 文件清单中的每个新增或修改文件都有任务承接，或明确标注为复用而无需修改。
- 适用的 DDL、核心服务伪代码、复杂时序和接口页面协作均有任务承接。
- 每个可执行任务有明确交付物和可观察完成条件。
- 涉及复杂状态流转、跨角色协同或审批闭环的标准/深度任务，是否包含至少 1 个正向黄金流转场景与 1 个逆向/异常防御场景的 GWT 验收用例。
- 任务编号连续，层级不超过两级。
- `_Depends:_`、`_Boundary:_` 与 `(P)` 没有明显冲突。
- 轻量任务没有被形式化拆成大量文件级或基础设施任务。
- 没有模板占位符、孤立任务或重复任务。

自检发现真实需求或设计缺口时停止写盘并报告用户；仅属于任务表述、顺序或粒度的问题直接修正。

### 第 6 步：写入待审任务清单

- 创建或更新 `spec/<spec-path>/tasks.md`。
- 不写入任何审批元数据，不宣称任务已批准。
- 首次生成时全部任务保持未完成状态。
- 增量更新时保留已有 `[x]`、`_Blocked:_`、`## Implementation Notes` 和人工修改内容。
- 若需求或设计变更导致已完成任务失效，先说明影响并请求用户确认，不自动改回未完成或删除历史记录。

写入后向用户汇总：

- 主任务数、子任务数和并行任务数。
- 需求覆盖情况与 GWT 核心端到端场景覆盖情况。
- 主要职责分组和关键依赖。
- 需要人工重点确认的任务粒度、顺序、范围与推迟项。

明确提示：当前 `tasks.md` 为待人工评审版本。用户提出意见时增量修改；用户明确确认任务清单后，才建议进入 `spec-impl`。

## 关键约束

- 不把简单 OA CRUD 拆成大量形式化基础设施任务；任务数量与实际改动规模匹配。
- 任务优先承接 `design.md` 已确认的复用方案，不得在任务阶段新增通用基础设施、改变状态/权限/流程或补造技术设计。

## 异常处理

- **缺少 requirements.md**：停止，提示先运行 `spec-requirements`。
- **缺少 design.md**：停止，提示先运行 `spec-design` 并完成人工确认。
- **需求 ID 非法**：停止，要求将需求标题和验收标准统一为数字 ID。
- **设计无法落地**：停止，列出缺失的文件路径、DDL、服务逻辑或流程信息。
- **已有 tasks.md**：进入增量更新模式，保护完成状态、阻塞记录和实施经验。
- **用户未确认任务清单**：保留人工评审提示，只继续修改，不建议开始实现。

## 输出

使用中文给出不超过 200 字的摘要，包括 `spec/<spec-path>/tasks.md` 路径、任务数量、需求覆盖情况、关键依赖和人工评审提示。
