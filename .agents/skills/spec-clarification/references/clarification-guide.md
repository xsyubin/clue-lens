# 需求澄清指南

## 澄清维度

按影响程度选择相关维度，不要求每个项目逐项询问。

| 维度 | 需要获得的结论 | 典型问题 |
| --- | --- | --- |
| 目标与痛点 | 为什么做、成功后改变什么 | 当前最耗时或最容易出错的环节是什么？ |
| 用户与职责 | 谁配置、谁使用、谁审批、谁维护 | 不同角色可以做什么，不能做什么？ |
| 功能范围 | 必须包含、明确排除、可推迟内容 | 本期必须闭环到哪一步？ |
| 核心流程 | 触发、主要步骤、结束状态 | 用户从哪里进入，完成后看到什么？ |
| 业务规则 | 计算、状态、限制、优先级 | 多条规则冲突时按什么顺序处理？ |
| 数据与口径 | 数据来源、业务含义、更新时效 | 指标如何定义，数据多久更新一次？ |
| 权限与可见性 | 功能权限、数据权限、默认拒绝策略 | 无授权时不可见、只读还是禁止访问？ |
| 输入与输出 | 输入控件、结果形态、导入导出 | 用户提供什么，系统返回什么？ |
| 异常与边界 | 空数据、重复、失败、超限、撤销 | 失败后如何提示，是否允许重试？ |
| 非功能约束 | 容量、响应、审计、安全、兼容性 | 最大数据量、响应时间或审计要求是什么？ |
| 相邻系统 | 谁负责上下游、依赖什么、不同步什么 | 哪些能力复用现有平台，哪些不在本规格负责？ |
| 演进与兼容 | 历史数据、旧流程、分期范围 | 上线后旧数据和旧入口如何处理？ |

## 提问优先级

先按依赖关系排序：被依赖的决策先问，否则后续问题会因为前一个答案作废。依赖相同时，再按以下影响度顺序处理：

1. 会改变产品定位或工作量级的分叉，例如“仅专业人员配置”与“业务人员零代码配置”。
2. 涉及数据泄露、合规、资金或不可逆操作的规则。
3. 决定核心用户流程是否闭环的缺口。
4. 影响验收的容量、性能、导入导出和异常处理。
5. 可留到设计阶段的实现偏好。

低影响细节可以给出建议默认值并请求确认，不要让它们阻塞高影响问题。

## 问题写法

优先使用“当前理解 + 分歧点 + 影响 + 问题 + 我的建议”的结构：

> 当前理解：业务管理员可以自行配置报表。若要求完全不懂数据结构的人员也能配置，就需要额外的业务语义和字段关系能力，范围会明显扩大。这里的目标用户是懂业务但不懂 SQL 的管理员，还是仍需懂表结构的实施人员？
>
> 我的建议：按“懂业务但不懂 SQL 的管理员”定位。原始需求提到的使用者是各科室报表员，本期也没有配套的数据字典建设，面向实施人员的定位会让这个功能失去自助价值。

每个问题都要带上建议，让用户从“开放作答”变成“确认或推翻”——这既降低用户成本，也把你的理解偏差暴露出来供其纠正。建议必须标注为建议，不能写成既定结论。

避免：

- 一次罗列十几个没有优先级的问题。
- 只问“还有什么需求吗”。
- 只给选项不给推荐，把全部选择成本推给用户。
- 明明能查证的事实拿来提问，例如现有实现、配置或既有术语。
- 用技术名词诱导用户接受某个方案。
- 把代码库现状直接当作用户需求。
- 对已经明确的答案反复确认。

## 决策状态

- **已确认**：用户明确确认，或原始材料明确陈述且用户未提出冲突。
- **建议待确认**：Codex 基于上下文提出的建议，不能写成最终结论。
- **开放问题**：暂时无法回答，但不一定阻塞后续工作。
- **阻塞问题**：不解决就无法形成稳定需求或验收口径。
- **已推迟**：明确不在当前阶段解决，并记录后续归属。
- **已变更**：新结论替代旧结论，需记录原因和影响。

## 与后续阶段的边界

需求澄清文档应让 `spec-requirements` 能够回答：谁在什么条件下，需要系统表现出什么可观察行为，以及异常时怎样处理。

以下内容通常留给 `spec-design`：

- 表结构、字段类型与索引
- API 路径、请求响应结构
- Vue 组件、Java 类和文件路径
- 缓存、消息队列、架构模式
- 具体第三方库和版本

若某项技术限制直接改变用户行为，例如“单次最多导出 5000 行”，应把可观察约束写入澄清文档；实现方式仍留到设计阶段。
