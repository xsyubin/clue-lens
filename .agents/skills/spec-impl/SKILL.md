# 按设计实现

以 `design.md` 为实现依据，以 `tasks.md` 为执行顺序。直接编码并自动验证，不另建复杂的实现、评审和调试协议。

## 输入

按以下顺序确定目标规格目录：

1. 若用户明确提供 `spec/` 下的相对路径，将其作为目标路径。
2. 若用户提供完整路径，确认其位于当前项目的 `spec/` 目录下，并转换为相对路径。
3. 若用户未提供路径，但当前请求明确指向 `spec/` 下唯一的功能目录，可使用该目录，并向用户说明判断结果。
4. 若存在多个候选目录或无法确定目标，不得猜测；在读取规格或修改代码前先询问用户。
5. `$1` 仅作为兼容写法，例如 `$1=platform/audit`，不假设调用环境一定提供位置参数。

将最终确定的相对路径记为 `<spec-path>`；后续所有输入输出路径均使用 `spec/<spec-path>/...`。本阶段的唯一候选必须同时包含 `requirements.md`、`design.md` 和 `tasks.md`；如果用户只调用 `spec-impl` 且无法确定唯一候选，先询问目标规格目录，不得开始编码。

必须读取：

- `spec/<spec-path>/requirements.md`
- `spec/<spec-path>/design.md`
- `spec/<spec-path>/tasks.md`
- 项目根目录 `AGENTS.md`
- 当前任务对应的项目规范

若用户指定任务编号，只实现指定任务及其尚未完成的必要依赖；否则按 `tasks.md` 顺序实现全部未完成任务。

**并发与工作区隔离约束（防打架铁律）**：
- **单工作区默认顺序执行**：在当前单一工作区目录下，必须严格按照 `tasks.md` 的依赖 DAG **单代理顺序推进任务**。严禁在同一物理工作区中启动多个 Subagent 并发修改文件，避免代码相互覆盖与竞争死锁。
- **多 Subagent 并发的前置条件**：若需开启多代理并行开发，必须基于 `.agents/agent-manifest.yml` 约定，强制使用 `scripts/worktree-new.sh` 在独立 `.worktrees/` 目录下创建分支工作树。仅限标记为 `(P)` 且 `_Boundary:_` 互斥隔离的任务可派发并行，最终通过 Git 分支合并，严禁共享物理目录直接踩踏。

不读取或写入 `spec.json`。开始编码前，必须确认用户已经完成以下阶段确认：`clarification.md` 的需求澄清、`requirements.md` 的需求范围、`design.md` 的设计评审、`tasks.md` 的任务评审。仅凭显式调用本 Skill 不足以跳过这些门禁；缺少确认时停止编码并提示用户先完成对应阶段。

## 执行流程

### 第 1 步：确认实现范围

- 读取 `tasks.md`，跳过 `[x]` 已完成任务和明确 `_Blocked:_` 的任务。
- 从 `requirements.md` 获取任务引用的 EARS 验收契约（状态守卫 While、触发条件 When、异常拦截 If、全局不变量 The system shall）。
- 从 `tasks.md` 获取当前任务关联的 GWT 场景定义（Given-When-Then）。
- 从 `design.md` 获取应新增或修改的文件、DDL、服务逻辑、接口和流程约束。
- 检查工作区现有改动并保留用户修改，不覆盖或回滚无关变更。
- 若任务与设计冲突、设计引用的仓库不可用、关键文件路径缺失或无法确定实现方式，停止该任务并报告具体缺口，不自行扩展设计。
- 若 `requirements.md`、`design.md` 与 `tasks.md` 在状态、权限、流程、字段或接口契约上不一致，停止受影响任务并指出应回到需求、设计或任务阶段修正，不自行选择口径。

### 第 2 步：清理目标模块运行时 Mock

- 在开始真实实现前，检查目标模块及其直接关联的 API、路由、状态管理和配置，识别：
  - `mock` 目录或文件、Mock 路由、接口 stub、MSW/Mock.js 等运行时拦截；
  - 页面、Service 或 API 文件中的硬编码业务数组、固定分页结果和演示数据；
  - `useMock`、`mockEnabled`、环境变量等 Mock 开关及其分支；
  - 本地 JSON、静态 Promise、失败后回退到假数据等运行时兜底；
  - 指向上述 Mock 的 import、注册、路由、代理和配置引用。
- 区分运行时 Mock 与测试 fixture：单元测试、集成测试中的 fixture、builder、stub 默认保留，除非它们被生产/开发运行时代码引用或与已确认设计冲突。
- 若当前模块存在运行时 Mock，先删除 Mock 数据及其模块内引用、注册和开关，再开始实现真实页面、接口或服务逻辑；不得保留“真实接口失败后继续展示 Mock 数据”的隐式回退。
- 删除前检查工作区现有改动并保留用户修改。若 Mock 被其他模块共享，不直接删除共享文件；只移除当前模块的引用，并报告其他使用方和后续清理范围。
- 清理后使用文本搜索确认目标模块不再引用运行时 Mock，并检查 import、路由、配置和类型引用没有悬空。若仍有无法清理的 Mock 依赖，停止后续实现并报告具体文件和原因。
- 在输出中列出已删除或解除引用的 Mock 文件、开关和调用点；没有发现运行时 Mock 时明确说明检查范围和结果。

### 第 3 步：按设计编码

- 严格使用 `design.md` 中确定的源代码路径和职责。
- 前端新建业务页面遵循项目架构规范；Java/Maven 后端实现遵循仓库 `AGENTS.md` 和相关 `rules/`。
- 后端 Service 层 CRUD 的实现方式**统一裁决**，同类场景不得混用多种写法，`design.md` 未指定实现方式时按以下规则执行，不自行选择：
  - 单表增删改查、条件查询、分页：一律使用 MyBatis-Plus 基类方法 + `lambdaQuery` 链式条件（`this.save` / `this.updateById` / `this.removeById` / `this.getById` / `this.lambdaQuery()...one()/.list()/.page(Pages.formReqDto(...))`），**不得**为此新增 Mapper 方法或手写 SQL。
  - 方法结构、Converter 转换、`StringUtils.isNotBlank` 条件判空等写法，以 `ticket-biz/src/main/java/com/ticket/biz/service/TicketDispatchServiceImpl.java` 为标准样例，保持一致。
  - 仅当命中 `rules/03` §2「Mapper 应该承担的职责」（跨表 JOIN、聚合统计、批量状态流转等）时才新增 Mapper 方法，且 SQL 一律写在 Mapper XML 中，**禁止 `@Select`/`@Update` 等注解 SQL**。
  - 跨模块取数只走对方 `I*Service` 接口，不直接注入其他模块 Mapper（`rules/03`/`rules/04` 的跨模块边界）。
- 按以下优先级实现：复用现有页面和页面模式 → 复用现有 DTO、Service、Mapper 与接口模式 → 复用现有权限和流程能力 → 最后才新增当前业务专用实现。
- 不因单个功能新增通用组件、通用服务、基础设施或抽象层；确有跨模块复用需求时必须先回到 `design.md` 明确设计。
- 不擅自改变需求文档中的业务状态、权限、数据范围和流程；实现细节无法满足已确认口径时回到对应阶段处理。
- 后端代码、DDL 或后端测试只有在对应后端仓库已提供且处于当前工作范围时才实施；当前仅有前端仓库时，不伪造后端文件或宣称后端任务完成。
- 不进行与当前任务无关的重构。
- 不自动创建 Git 提交，不自动暂存文件。

### 第 4 步：边实现边验证

- 有现成单元测试时，修改相关代码后运行对应测试。
- 新增或修改核心业务规则、数据转换、状态处理等可独立测试逻辑时，对照关联的 EARS 异常分支（`If <异常条件>, then...`）补充必要的聚焦单测，确保参数校验、越权拦截与非法状态跃迁被代码严格防卫。
- 普通 CRUD 不强行引入新的测试框架、分层抽象、通用封装或形式化测试仪式；复用项目现有测试方式并覆盖关键校验、权限和数据写入结果。
- 纯页面布局或仓库没有合适测试基础时，不强制为形式完整编写低价值测试；改用结构检查、Lint、构建和必要的页面验证。
- 测试失败时先定位并修复当前改动造成的问题，然后重新运行。
- 若失败属于既有无关问题，记录命令、错误和判断依据，不掩盖也不擅自修改无关代码。

### 第 5 步：自动执行最终验证

全部目标任务实现后，自动执行当前仓库提供的标准命令。

根据仓库类型选择标准验证命令。本项目（TypeScript/Next.js）默认执行：

```bash
npm run typecheck
npm test
```

涉及构建配置、路由、依赖、跨模块改动或较大范围修改时，再执行：

```bash
npm run build
```

#### 核心 GWT 端到端场景化测试门禁（强制执行）

若 `tasks.md` 中包含 **`GWT 场景`** 的集成验证任务：
1. 必须编写或运行对应的自动化测试脚本（或端到端模拟测试用例），真实运行 GWT 业务旅程。
2. 真实执行测试并校验断言：
   - **正向黄金旅程**：数据准备（Given） $\rightarrow$ 提交/流转动作（When） $\rightarrow$ 状态跃迁与时间轴留痕（Then / And）；
   - **逆向与异常阻断**：前置状态与非法输入/驳回（Given / When） $\rightarrow$ 异常拦截、状态回退与报错提示（Then / And）。
3. 必须在测试运行输出中确认断言全部绿灯（PASS）。严禁跳过实际测试运行仅凭静态编译推断通过。

Java/Maven 后端仓库应先读取 `pom.xml`、模块配置和 CI 脚本，确定对应模块的标准命令；通常至少执行相关模块测试和编译，例如：

```bash
mvn test -pl <module> -am
mvn package -pl <module> -am -DskipTests
```

涉及数据库、事务、AOP 或跨模块集成时，补充项目已有的集成测试或验证命令。不要执行与当前任务无关的前端命令。

涉及关键页面交互且已有对应自动化用例时，执行相关测试用例。不要无条件运行与本次功能无关的全部测试。

若在其他仓库实现后端任务，优先从该仓库的构建文件、任务脚本和 CI 配置中确定标准测试与构建命令，不凭空猜测命令。

最终验证失败时：

1. 修复当前实现引入的问题。
2. 重新运行失败命令与 GWT 测试。
3. 仍不能通过时停止，不把对应任务标记为完成，并报告失败命令和关键错误。

### 第 6 步：更新任务状态

- 只有代码已实现、标准验证命令通过，且 **`tasks.md` 中声明的 GWT 场景测试全部通过断言** 后，才将 `tasks.md` 中该任务从 `[ ]` 改为 `[x]`。若 GWT 测试未运行或存在失败断言，一律保持未完成状态。
- 可选任务 `[ ]*` 完成后改为 `[x]*`。
- 部分完成、未测试或验证失败的任务保持未完成状态。
- 真实外部阻塞可在任务下追加 `_Blocked: 原因_`，不得用阻塞标记掩盖可在仓库内修复的问题。
- 保留 `## Implementation Notes`；只有出现会影响后续任务的实现事实时才追加简短记录。

## 完成标准

- 实现与 `requirements.md` 的 EARS 验收行为与状态防卫完全一致。
- 文件、数据结构、服务逻辑和流程符合 `design.md`。
- 目标模块不存在仍会参与运行时行为的 Mock 数据、接口桩、Mock 路由、Mock 开关或假数据回退；测试 fixture 不受此条限制。
- `tasks.md` 中所有包含 GWT 验收场景的任务已通过自动化测试或集成用例验证并全部通过。
- 目标任务在 `tasks.md` 中有真实完成状态。
- 前端仓库的 `npm run typecheck`、相关单元测试、GWT 自动化测试和必要的 `npm run build` 通过，或 Java/Maven 后端仓库中已确定的对应检查、测试和构建命令通过。
- 没有通过测试或验证时，不宣称实现完成。

## 输出

简要报告：

- 已完成和未完成的任务编号。
- 主要改动文件。
- Mock 检查范围、清理内容或未发现 Mock 的结论。
- 实际运行的测试、检查和构建命令及结果。
- GWT 核心场景测试验证结果（执行场景名称、通过状态与关键断言）。
- 未解决问题、既有无关失败或外部阻塞。

不要输出评审裁决、子代理状态协议或自动提交信息。

## 异常处理

- **规格文件缺失**：停止并提示先完成对应前置阶段。
- **设计与代码库不一致**：停止受影响任务并请求修正 `design.md`。
- **需求、设计、任务不一致**：根据冲突来源回退到 `spec-requirements`、`spec-design` 或 `spec-tasks`，不在实现阶段自行裁决。
- **Mock 无法安全清理**：共享 Mock 仍被其他模块依赖、Mock 与真实接口契约无法对应或删除会超出当前任务范围时，停止后续实现并报告依赖关系，不带着 Mock 继续编码。
- **只有前端仓库但任务含后端实现**：完成可独立实施的前端任务，后端任务保持未完成并说明缺少的仓库或上下文。
- **测试命令不存在**：从 `package.json`、`pom.xml`、构建文件或 CI 配置重新确认；确实没有时说明未能运行该类测试。
- **会话中断**：重新运行本 Skill，依据 `tasks.md` 的 `[x]` 状态继续未完成任务。

## 并发执行与工作区隔离铁律（防踩踏机制）

为了杜绝多 Agent 协同编码时对相同文件发生写冲突或 Git 踩踏，必须严格遵守以下执行边界：

1. **单工作区保护（默认防线）**：
   - 当在当前主工作区直接执行实现时，执行模型强制为**单代理单线程顺序执行**。
   - 必须按照 `tasks.md` 的依赖 DAG 拓扑分阶段依次推进（基础准备 $\rightarrow$ 核心算法 $\rightarrow$ Actions $\rightarrow$ 页面 $\rightarrow$ 验收）。
   - 严禁在共享工作区内派发无隔离的并发子代理，防止同一文件被双写覆盖。

2. **多 Subagent 并发隔离要求**：
   - 仅当明确启用了 Git Worktree 物理隔离机制时，才允许并行处理标记为 `(P)` 的任务；
   - 每个子代理必须在独立的 `.worktrees/ticket-lite-<task>` 目录下运行（通过 `scripts/worktree-new.sh`），拥有隔离的 Git 分支与文件副本；
   - 子代理之间修改的组件与职责边界（`_Boundary:_`）必须 100% 互斥，严禁多子代理重叠碰触同一文件；
   - 子代理开发测试绿灯后，由主代理或人工统一进行 Git 分支 Merge，严禁直接无序提交。
